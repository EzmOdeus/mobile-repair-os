# خطة التطوير: ما تم تنفيذه وما يأتي بعد ذلك

## مقارنة مع مراحل الدراسة (قسم 29)

| المرحلة | نطاق الدراسة | الحالة في هذا التنفيذ |
|---|---|---|
| **Phase 0** – Discovery | 20 مقابلة + اختبار willingness-to-pay | ⏳ **غير منفَّذ** — عمل ميداني، لا يمكن تنفيذه برمجيًا |

**قيود الدراسة التي التُزمت بها:**
- ❌ لا Marketplace → **أُضيف لاحقًا بطلب من المالك**: ماركت بلس للعروض والتواصل فقط، بلا مدفوعات أو تسليم داخل النظام
- ❌ لا AI تشخيصي كامل → فقط اقتراحات موثقة مع إخلاء مسؤولية
- ❌ لا ERP محاسبي ضخم → مالية تشغيلية للتشغيل اليومي
- ❌ لا تطبيقين منفصلين للعميل → صفحة تتبع واحدة

## قدرات تشغيلية مكتملة (ما بعد MVP)

| القدرة | التنفيذ |
|---|---|
| دورة مشتريات كاملة | أمر شراء (مسودة → اعتماد → استلام كلي/جزئي → إلغاء)، دفعات موردين، أعمار دائنين، كشوف حساب |
| جرد وتسويات مخزون | محضر جرد لكل فرع يقارن المعدود بالرصيد ويُنشئ حركات تسوية تلقائية |
| تحويلات بين الفروع | إرسال/استلام مع حركتي `transfer_out`/`transfer_in` وحالات انتقال واضحة |
| تقييم المخزون والاستهلاك | تقييم بالتكلفة/البيع والهامش المحتمل + تقرير استهلاك ومعدل فشل القطع |
| تقارير مالية | أرباح وخسائر، إقرار ضريبة القيمة المضافة، أعمار مستحقات، كاشير، كشوف عملاء وموردين |
| الخزينة والورديات | فتح/إغلاق وردية لكل فرع برصيد افتتاحي، ربط تلقائي للمدفوعات والمصروفات النقدية بالوردية المفتوحة، النقد المتوقع مقابل المعدود والفرق عند الإغلاق، ومنع تعديل مصروفات وردية مغلقة |
| ماركت بلس وبورصة الأسعار | سوق عام بين المراكز بمراجعة منصة + سوق داخلي بين الفروع، إعلانات وصور وعروض شراء، دليل أسعار مرجعي ومؤشر مشتق من الإعلانات مع تقييم جهاز وسعر مقترح |
| عزل الفروع في الواجهة والـAPI | مبدّل فرع نشط + `x-branch-id` + `requireBranchAccess` على التذاكر والعروض والفحص والضمان والمخزون والمشتريات والتقارير |
| نقاط بيع مرتبطة بالفرع | الكميات المعروضة والمخصومة من رصيد الفرع النشط، ورفض البيع بدون فرع محدد |
| إدارة مستخدمين وفروع كاملة | تعديل/تعطيل/تفعيل، أدوار وفروع مسموحة، إعادة تعيين كلمة المرور من لوحة الإدارة |
| المصادقة الثنائية (2FA) | TOTP (RFC 6238) متوافق مع تطبيقات المصادقة، سر مشفّر AES-256-GCM، 8 رموز استرداد أحادية الاستخدام، تحدّي دخول قصير العمر، إبطال جلسات ما قبل التفعيل، وإعادة تعيين إدارية عند فقد الهاتف |
| PWA وعمل بدون اتصال | manifest عربي RTL وأيقونات maskable وService Worker يخزّن أصول الواجهة فقط، صفحة `/offline.html`، وطابور تذاكر محلي (`localStorage`) مرتبط بالمؤسسة/المستخدم/الفرع يُزامَن تلقائيًا عند عودة الشبكة مع تصنيف الأخطاء الدائمة وإمكانية إعادة/حذف يدوي |
| Idempotency لإنشاء التذاكر | `clientRequestId` اختياري (8–120 حرفًا) مع فهرس فريد لكل مؤسسة؛ إعادة الإرسال تُرجع نفس التذكرة برمز `idempotentReplay` دون تكرار العميل/الجهاز/التذكرة، وآمنة تحت سباق الطلبات المتزامنة |
| طباعة المستندات | عزل `#print-area` لطباعة إيصال POS والفاتورة وكشوف الحساب والتقارير عبر المتصفح |
| نسخ احتياطي مجدول | نسخة JSON كاملة كل 24 ساعة + لقطة مجلد `uploads` بنفس الطابع الزمني، احتفاظ بآخر 14 نسخة، تشغيل/تنزيل/استعادة من مسارات المنصة |
| تكامل مستمر (CI) | GitHub Actions: تثبيت نظيف + `typecheck` + اختبارات Vitest على MongoDB خدمة + بناء الإنتاج لكل commit وPR |

## قدرات SaaS المكتملة (طبقة المنصة)

هذه الطبقة هي ما يحوّل النظام من تطبيق لنظام تشغيل مركز واحد إلى **منصة SaaS متعددة المستأجرين**:

| القدرة | التنفيذ |
|---|---|
| تسجيل ذاتي (Self-signup) | `POST /auth/register` ينشئ مركزًا + مالكًا + فرعًا رئيسيًا ويبدأ تجربة مجانية 14 يومًا |
| كتالوج باقات بحدود | `constants/plans.ts` — starter (تجربة 14 يومًا فقط) / growth / pro / enterprise، بأعلام `trialOnly` و`selfService` و`customPricing` |
| فرض حدود الباقة | `planService` يمنع تجاوز المستخدمين/الفروع/التذاكر + `subscriptionWriteGuard` يحوّل المركز المنتهي لوضع قراءة فقط |
| دورة حياة الاشتراك | تجربة → ساري → مهلة سداد (past_due، افتراضي 7 أيام) → إيقاف (cancelled)، بنقل تلقائي دوري عبر `subscriptionScheduler` |
| مدير منصة (Platform Admin) | دور `platform` بصلاحيات `platform:*` لا تُمنح لأي دور مركزي، ومسارات `/platform` لإدارة كل المراكز |
| لوحة إدارة المراكز | قائمة المراكز مع حالة الاشتراك والاستخدام، إحصاءات المنصة (MRR، توزيع الحالات)، إيقاف/تفعيل مركز، تفعيل اشتراك بسعر مخصص/دفعة اختيارية، تغيير باقة |
| سجل مدفوعات وطلبات تجديد | `SubscriptionPayment` لكل سداد (طريقة/مرجع/فترة تغطية) + `SubscriptionRenewalRequest` بطلب معلّق واحد لكل مركز، ومراجعة من المنصة باعتماد (يفعّل ويسجّل دفعة مرتبطة) أو رفض بسبب موثّق |
| تذكيرات ما قبل الانتهاء | فحص دوري عند 7/3/1 أيام (`SUBSCRIPTION_REMINDER_DAYS`) مع منع تكرار التذكير لنفس الدورة |
| تقرير إيرادات الاشتراكات | `GET /platform/revenue` — المحصّل والتوزيع حسب الباقة/طريقة الدفع وآخر المدفوعات ضمن نطاق تاريخي |
| حماية من تصعيد الصلاحيات | دور المنصة وصلاحياتها مستثناة من إنشاء المستخدمين والتخصيص الفردي في مسارات المركز |
| حساب مدير المنصة | يُنشأ تلقائيًا في البذرة (idempotent): `platform.admin` على مؤسسة مرجعية داخلية `platform-hq` |
| استعادة كلمة المرور | بريد → رمز 30 دقيقة مُجزّأ → إعادة تعيين، مع صفحتي واجهة `/forgot-password` و`/reset-password` |
| عزل المستأجرين | `tenantPlugin` يفرض `organizationId` على كل استعلام — مُختبر في الـE2E بمركزين متوازيين |
| بوابة عميل عامة | تتبع الجهاز بالرمز والموافقة الرقمية على العروض بدون تسجيل دخول |
| سجل تدقيق لكل عملية | بما فيها عمليات إدارة المنصة — تُسجّل في سجل المركز المستهدف بسياق فاعل صريح |

> نقطة الربط المستقبلية للدفع الإلكتروني (Paymob): `subscriptionService.activateSubscription` هي الدالة الوحيدة التي يحتاج webhook الدفع لاستدعائها.

## ما يحتاج عملًا قبل الإطلاق التجاري

### أولوية عالية (إلزامية)

1. **توسيع الاختبارات الآلية** — CI يفرض الآن `typecheck` و66 اختبارًا و`build` وPlaywright E2E على كل commit، لكن التغطية ما زالت غير كافية لمنطق المشتريات والمالية المتقدم والضمان (الأولوية لإضافة اختبارات تكامل لخدمات التقارير والورديات على بيانات أكبر).
2. **WhatsApp Business API** — طبقة القوالب جاهزة و`WHATSAPP_MODE=cloud-api` مدعوم في الخدمة، لكن يحتاج:
   - ضبط `WHATSAPP_PHONE_NUMBER_ID` و`WHATSAPP_ACCESS_TOKEN`
   - قوالب معتمدة من Meta
   - Webhook لاستقبال ردود العملاء
3. **النسخ الاحتياطي الكامل** — منفّذ: تصدير JSON لكل مؤسسة، جدولة كل 24 ساعة مع احتفاظ 14 نسخة، ولقطة مجلد `uploads` محليًا (وعلى S3 عبر Versioning). المتبقي:
   - اختبار استعادة كامل على بيئة منفصلة (قاعدة + ملفات)
   - نسخ خارج الموقع (Offsite) — تُنسخ مجلد `backups` دوريًا إلى تخزين منفصل
4. **مراجعة قانونية** — خصوصية البيانات (قانون حماية البيانات الشخصية المصري)، سياسة الاحتفاظ، وشروط جمع صور الأجهزة والـIMEI.
5. **مراجعة أمنية خارجية (Pen-test)** — المصادقة الثنائية نُفّذت الآن (TOTP + رموز استرداد + إعادة تعيين إدارية + إبطال الجلسات القديمة)، ويبقى اختبار اختراق مستقل ومراجعة إعدادات الإنتاج قبل الإطلاق.
6. **إرسال بريد/SMS فعلي لرمز الاستعادة** — التدفق كامل ومُختبَر، والرمز يُعاد في الاستجابة بوضع التطوير فقط؛ الإنتاج يحتاج مزوّد بريد (مثل Resend/SMTP) أو SMS بمصر.

### أولوية متوسطة

7. **الأداء والعزل في الإنتاج** — تشغيل MongoDB كـReplica Set وتفعيل Transactions للمعاملات المتعددة المستندات. بيع POS مؤمَّن الآن على standalone بترتيب مسودة → خصم → دفعة → تثبيت + تعويض تلقائي واسترداد عند الإقلاع، لكن Transactions تبقى الأفضل عند توفير replica set.
8. **توليد PDF** — منفّذ للفواتير على الخادم مع QR ضريبي (ويعمل مع الطباعة المعزولة لبقية المستندات). المتبقي: توليد PDF لكشوف الحساب والتقارير وإرسالها تلقائيًا عبر واتساب/البريد.
9. **تتبع مكالمات العملاء** — لقياس المؤشر المطلوب «عدد الاتصالات المتكررة».
10. **البحث العربي التقريبي** — حاليًا regex؛ يحتاج normalizer للنص العربي (همزات، تشكيل، أرقام عربية).
11. **الاختبار على بيانات أكبر** — اختبار الأداء مع آلاف التذاكر.

> ملاحظة: «مهمة مجدولة للـSLA» نُفّذت وحُذفت من هذه القائمة — `slaScheduler.ts` يعمل داخل الـAPI كل `SLA_SCAN_INTERVAL_MINUTES` دقائق (انظر `server.ts`).

### أولوية منخفضة / مستقبلية

12. **AI Repair Assistant (Phase 4)** — البنية جاهزة:
    - `KnowledgeArticle` مع خطوات وأسباب ونتائج تاريخية
    - `GET /knowledge/suggest` يقبل Model + Symptom ويعيد اقتراحات
    - الناقص: تكامل LLM/RAG مع الإشارة لمصدر المعرفة، وضوابط منع التعليمات الخطرة، وHuman-in-the-loop.
    - يجب أن يبقى **مساعدًا للفني لا بديلًا عن الفحص**، وألا يقدّم تخمينًا كحقيقة.
13. **Industry Intelligence (Phase 5)** — بيانات مجهولة ومجمّعة عن الأعطال ومعدلات الضمان. يحتاج قاعدة عملاء كافية + إطار خصوصية.
14. **API للتكاملات الخارجية** — مفاتيح API، Webhooks، توثيق عام.
15. **تكامل الموردين إلكترونيًا** — طلب قطع آلي ومقارنة أسعار (Phase 5).

## توصيات ترتيب التنفيذ

```
الأسبوع 1–2:  اختبارات وحدة + backup/restore مُختبَر               ✅ منفَّذ (66 اختبارًا + نسخ مجدول؛ يبقى اختبار استعادة على بيئة منفصلة)
الأسبوع 3–5:  PWA + Offline queue للتذاكر الحرجة                    ✅ منفَّذ
الأسبوع 6–8:  WhatsApp Cloud API + Webhook + قوالب معتمدة            ⏳ التالي
الأسبوع 9–10: مراجعة قانونية + مراجعة أمنية خارجية
الأسبوع 11–12: اختبار حمل + Replica Set
```

نقطة البداية الموصى بها في الدراسة — **مركز متوسط بعدة فنيين** — مدعومة بالكامل في هذا التنفيذ، والبيانات التجريبية تحاكي مركزًا بثلاثة فروع و5 فنيين و84 تذكرة عبر 7 أشهر.

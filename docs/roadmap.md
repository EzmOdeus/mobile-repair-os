## مؤشرات نجاح الـPilot (قسم 33) — جاهزة للقياس

كل المؤشرات المطلوبة في الدراسة مُنفَّذة قابلة للقياس عبر `GET /analytics/pilot-kpis`:

| المؤشر المطلوب | التنفيذ |
|---|---|
| زمن إنشاء التذكرة | `RepairStatusHistory.durationMinutes` من `created` |

| متوسط زمن الإصلاح | `turnaround.avgTotalRepairHours` |
| الأجهزة المتأخرة | `sla.breached` + `tickets/sla-report` |
| نسبة الموافقات | `Approval` decisions |
| Warranty Return Rate | `warranty/intelligence` |
| نسبة اجتياز QC من أول مرة | `quality-checks/stats` |
| دقة المخزون | `lastCountedAt` في رصيد الفروع |

> الأرقام المستهدفة موضوعة كإطار مبدئي؛ الدراسة تنصّ على تحديدها بعد قياس خط الأساس في المراكز التجريبية.

## ما يحتاج عملًا قبل الإطلاق التجاري

### أولوية عالية (إلزامية)

1. **اختبارات آلية دائمة** — يوجد اختبار E2E شامل (70 تحققًا)، لكن لا توجد اختبارات وحدة (unit tests) لتغطية أخطاء الانحدار.
2. **PWA كامل** — Service Worker، تثبيت، وطابور Offline. الدراسة تعتبر Offline عنصرًا معماريًا مبكرًا، والمخطط موجود في قسم 26 لكنه غير منفَّذ.
3. **WhatsApp Business API** — طبقة القوالب جاهزة و`WHATSAPP_MODE=cloud-api` مدعوم في الخدمة، لكن يحتاج:
   - ضبط `WHATSAPP_PHONE_NUMBER_ID` و`WHATSAPP_ACCESS_TOKEN`
   - قوالب معتمدة من Meta
   - Webhook لاستقبال ردود العملاء
4. **النسخ الاحتياطي والاستعادة** — لا يوجد سكربت backup/restore مُختبَر. يحتاج:
   - `mongodump` مجدول
   - نسخ مجلد `uploads`
   - اختبار استعادة كامل
5. **مراجعة قانونية** — خصوصية البيانات (قانون حماية البيانات الشخصية المصري)، سياسة الاحتفاظ، وشروط جمع صور الأجهزة والـIMEI.
6. **تفعيل المصادقة الثنائية (2FA)** للحسابات المالكة والمديرين.

### أولوية متوسطة

7. **الأداء والعزل في الإنتاج** — تشغيل MongoDB كـReplica Set، تفعيل Transactions للمعاملات المتعددة المستندات (بيع POS مثلًا)، ومراجعة الفهارس تحت حمل حقيقي.
8. **توليد PDF** — إيصال حراري، فاتورة، وتقرير تذكرة. حاليًا الطباعة من المتصفح فقط.
9. **مهمة مجدولة للـSLA** — `scanSlaBreaches` موجودة لكن لا يعمل لها scheduler. يحتاج cron job.
10. **تتبع مكالمات العملاء** — لقياس المؤشر المطلوب «عدد الاتصالات المتكررة».
11. **البحث العربي التقريبي** — حاليًا regex؛ يحتاج normalizer للنص العربي (همزات، تشكيل، أرقام عربية).
12. **الاختبار على بيانات أكبر** — اختبار الأداء مع آلاف التذاكر.

### أولوية منخفضة / مستقبلية

13. **AI Repair Assistant (Phase 4)** — البنية جاهزة:
    - `KnowledgeArticle` مع خطوات وأسباب ونتائج تاريخية
    - `GET /knowledge/suggest` يقبل Model + Symptom ويعيد اقتراحات
    - الناقص: تكامل LLM/RAG مع الإشارة لمصدر المعرفة، وضوابط منع التعليمات الخطرة، وHuman-in-the-loop.
    - يجب أن يبقى **مساعدًا للفني لا بديلًا عن الفحص**، وألا يقدّم تخمينًا كحقيقة.
14. **Industry Intelligence (Phase 5)** — بيانات مجهولة ومجمّعة عن الأعطال ومعدلات الضمان. يحتاج قاعدة عملاء كافية + إطار خصوصية.
15. **API للتكاملات الخارجية** — مفاتيح API، Webhooks، توثيق عام.
16. **تكامل الموردين إلكترونيًا** — طلب قطع آلي ومقارنة أسعار (Phase 5).

## توصيات ترتيب التنفيذ

```
الأسبوع 1–2:  اختبارات وحدة + backup/restore مُختبَر
الأسبوع 3–5:  PWA + Offline queue للتذاكر الحرجة
الأسبوع 6–8:  WhatsApp Cloud API + Webhook + قوالب معتمدة
الأسبوع 9–10: 2FA + مراجعة قانونية + PDF
الأسبوع 11–12: اختبار حمل + Replica Set + scheduler الـSLA
```

نقطة البداية الموصى بها في الدراسة — **مركز متوسط بعدة فنيين** — مدعومة بالكامل في هذا التنفيذ، والبيانات التجريبية تحاكي مركزًا بثلاثة فروع و5 فنيين و84 تذكرة عبر 7 أشهر.
